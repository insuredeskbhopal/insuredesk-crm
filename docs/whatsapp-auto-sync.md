# WhatsApp automatic synchronization

Scope: the Operations Hub WhatsApp page and the dashboard's My Primary WhatsApp control.

| File | Observed problem / reason for change | Minimum change | Impact and verification |
| --- | --- | --- | --- |
| `src/app/lib/whatsapp-sync.js` | No shared update source across the table and two selectors; existing browser event works in only one tab. Five-second global polling would increase load on every CRM page. | Share one timer per tab: five seconds while Setup is mounted, otherwise the selector's original thirty seconds. Refresh on visibility/focus/network recovery and use native BroadcastChannel for successful-action notifications. Messages contain only an update category. | Duplicate controls share the existing request cache. Hidden tabs pause reads. Verify interval changes on mount/unmount, immediate notifications, no echoes, cleanup, and independent authenticated reads in each tab. |
| `src/app/components/whatsapp/PrimaryWhatsAppSelector.js` | Selection refresh is limited to the initiating window; repeating full account reads also fetches unused metrics and staff lists. | Subscribe to shared updates and notify after a successful save. Use compact background snapshots and discard responses predating an account-change notification. | Retains the existing preference API and backend authorization. Verify table/header agreement without reload, permission revocation, and a delayed stale response after selection. |
| `src/app/api/operations/whatsapp/sessions/route.js` | Background account/status reads repeat gateway metrics and administrator staff-list queries. | Add optional GET `?view=sync` which omits only metrics/staff reads and fields. Preserve account filtering and the default GET response. | No mutation, schema or gateway behavior changes. Verify compact/full account snapshots match and tenant/permission isolation remains enforced. |
| `src/app/components/operations/WhatsAppSetupPage.js` | Account rows stop updating after initial load; health stops polling when connected; several actions never notify the selector; queue and templates do not automatically update. | Subscribe to shared updates, notify after successful mutations, refresh silently, and retain current queue pagination/filter through the subscription. Refresh editable templates only when visible or explicitly notified; merge around unsaved drafts and edits made during a save. Reconcile the open access dialog while retaining pending checkbox intentions. Abort/ignore superseded responses. | Existing routes, mutation payloads, permissions and session lifecycle remain intact. Verify external disconnection/access changes, immediate primary changes, queue status updates, draft preservation, pending grant rollback, no flicker, and no duplicate requests. |
| `src/app/lib/client-api.js` | Clearing a pending cached request still lets its late success/failure overwrite or remove a newer request. Account changes now require immediate invalidation while automatic reads may be pending. | Permit URL-scoped invalidation and let a pending request change the cache only if it still owns that entry. No-argument clearing retains its existing behavior. | All other cache consumers retain their API. Verify unrelated cached auth data survives account invalidation and old success/failure cannot overwrite/evict a newer result. |
| `tests/whatsapp-ui-sync.test.js` | Synchronization and stale-request races need repeatable evidence. | Add scoped tests with fake timers, native-channel substitutes and controlled request completion. | No live database, WhatsApp session or messages are touched. |

Local successful actions and same-origin open-tab notifications refresh immediately after the server accepts the action. External changes are detected on the next five-second check while Setup is mounted, or thirty-second check elsewhere, plus network response time. QR pairing retains its existing four-second check. This is automatic synchronization, **not server-pushed real-time delivery**. Hidden tabs pause background reads and refresh when visible again. Sender health on background refresh comes from the same authorized account snapshot; initial/explicit status checks remain available. Metrics update on full refresh, and opening Manage access refreshes the staff list once. No gateway restart, database/schema change, new dependency or session disconnection is involved.

## Verification evidence

- Final focused suite (account authorization, UI synchronization, policy count cache, navigation loading and lead reports): 59 tests passed. The full suite also passed all WhatsApp account, gateway-group, multi-account, QR-lifecycle, worker and synchronization tests. See [server load audit](server-load-audit.md) for full-suite limitations.
- Full ESLint: zero errors, 50 warnings. Isolated production build: passed, with jose Edge Runtime compatibility warnings.
- Isolated browser checks with real UI components and mocked APIs: automatic external disconnection/access changes (measured at 4,957 ms in the final check), immediate primary agreement between table/header, native cross-tab notification, independently retained peer preference, delayed stale-response protection, unsaved text/attachment preservation, unedited template updates, queue updates, and open access-dialog updates passed without runtime errors.
- Existing isolated UI checks: initial account request deduplication, checkbox feedback and failed-save rollback, group search/selection, modal portal placement, template save payloads, and responsive account rows at 15 widths passed.
- Request budget: a 10,500 ms passive Setup window produced two compact account reads shared by the table and both selectors, two queue reads, zero full account/status/template reads. Compact snapshots omitted staff/metrics without clearing existing staff options. A 6,000 ms hidden window produced zero automatic reads.
- No live messages were sent; no live account, permission, database, or session changes were made. No push or deployment was performed. Deployment behavior, production CPU/memory and live multi-device timing have not been verified.

## Connected-account table presentation

The previous table had excessive visual whitespace, plain status/access values, a blank primary-action cell for the selected account, and inconsistent visual emphasis between controls. The redesign changes only the account-table CSS in `WhatsAppSetupPage.module.css` and its presentation markup in `WhatsAppSetupPage.js`: a muted header, tighter rows, wider status column, soft status/access badges, a subtle primary-row tint, rounded sender controls, a non-interactive Selected indicator, and readable status capitalization. The existing separate action columns and faint vertical separators remain.

Impact of the presentation changes is limited to table appearance and responsive layout. Action handlers, their visibility/disabled permission conditions, authentication, API payloads and session handling are unchanged by the redesign. The isolated account-row browser verification passed at 15 widths from 320 to 1920 pixels, including aligned columns, single-line Manage access labels, no overlapping controls or horizontal overflow, permission restrictions, primary selection, and dialog/confirmation behavior. Desktop and mobile screenshots were inspected. No live session was modified or code pushed.
