# Server load and regression audit — 9 October 2026

This audit addresses unnecessary work found in the current implementation. It does not establish production CPU/RAM savings, zero server load, or that every CRM workflow passes. Existing data and WhatsApp sessions were not modified. No dependency, database/schema, PDF parser, OCR configuration, report calculation or deployment change was made.

## What was inspected and left alone

- Public homepage: two read-only HEAD requests showed canonical redirection and a successful `X-Vercel-Cache: HIT`, `X-Nextjs-Prerender: 1` response. No homepage/cache/CDN settings were changed.
- PDF ingestion: uploads process sequentially; OCR follows insufficient text quality, default local OCR limit is two pages and worker cleanup is present. Motor, other insurer/category extraction, neutral helpers, schemas and training modules were left untouched.
- Claims list: bounded page size and lightweight document counts rather than embedded file bodies. Reporting: selected-domain query plans and bounded scans already exist. Without production slow-query measurements, changing SQL or indexes would be speculative.
- Attendance heartbeat: existing visibility behavior affects attendance recording. It was not reduced merely to remove requests.
- Authentication, account ownership, personal sender preference, session management, queued sender identity and automation sender routing were preserved. QR pairing retains its existing four-second loop; no gateway process was restarted.

### Remaining failures and limits

The final full suite has existing failures in birthday RBAC error-text expectations (2), claims pagination (1), client Google login (1), client-ID request workflow (2), client policy save/update (3), dashboard overview expectations (6), ICICI CPM extraction under the full run (1), lead-generation signature expectation (1), modal source-layout assertion (1), monthly attendance calendar (1), performance source assertions (3), reporting category expectation (1) and warehouse record-column expectation (1). All were already failing in the pre-change workspace run. Some assertions inspect source text; this does not make the entire set safe to dismiss. Actual failing workflows need their own investigation before a clean production-readiness claim.

No production load test, live PDF upload, live message send, account disconnect, schema mutation, push or deployment was performed. Browser checks use isolated fixtures. Production gateway/database latency, CPU/RAM, throughput and multi-device behavior have not been measured. Request/query reductions are verified locally; whole-site response time and production load cannot be guaranteed from them. The policy count cache is per process, so separate server instances do not share its pending work.
